# ADR-023: Граф памяти — обычные таблицы PostgreSQL вместо Apache AGE

## Status

Accepted (2026-10-02, решение владельца). Реализация п.1–4 и кодовой части п.7 —
TASK-001284 (раздел «Реализация» ниже); перенос данных (п.5) — TASK-001285 (раздел
«Перенос данных» ниже, там же правки ревью TASK-001284), замер
(п.6) — TASK-001286 (раздел «Замер» ниже; контрольный прогон на копии staging —
TASK-001293/TASK-001370, выкатка одобрена владельцем 2026-10-03), образ базы и среда тестов исполнителя — TASK-001287. Заменяет в части
хранилища графа [ADR-016](ADR-016-context-memory-engine.md) («хранилище остаётся
PostgreSQL 16 + AGE + pgvector») и снимает вопрос движка, закрытый
[ADR-014](ADR-014-delivery-form-storage-not-language.md) и
[ADR-015](ADR-015-ladybugdb-spike-rejected.md): PostgreSQL остаётся, AGE уходит.
Делает ненужным обход планировщика из [ADR-010](ADR-010-graph-latency-jit-not-rust.md)
(подтверждено замером п.6). Связано с решением суперпроекта об объединении баз платформы
в один кластер PostgreSQL (TAI-ADR-0065, готовится): без AGE база памяти входит в
общий кластер на равных с остальными.

## Context

### Что сервис берёт от AGE

Модули `graph/store.py` и `graph/facts.py` (около 2800 строк вместе с
`graph/`), порядка 50 запросов Cypher. Все они собираются нашим кодом; наружу
Cypher не выходит ни в HTTP-контракте, ни в инструментах агентов. По сути это CRUD
поверх графа свойств:

- `MERGE` узла по `(label, natural_key, namespace)` и ребра по `fact_id` или по
  паре концов, пакетно через `UNWIND`;
- `DETACH DELETE` узла, редакция и purge по `observation_id` (ADR-001, ADR-002);
- слияние дубликатов: перенос рёбер на выжившего и удаление дубля (ADR-022);
- обход не глубже двух хопов, причём итеративно по одному хопу: переменная длина
  `[*1..2]` на хаб-узлах взрывалась комбинаторно (`store.py`, комментарий у
  сборки подграфа);
- графовые алгоритмы (кластеры, сообщества) считаются в Python через networkx
  (`graph/projection.py`, `graph/cluster.py`), а не в базе.

### Во что AGE обходится

1. **Планировщик.** AGE даёт оценку кардинальности в 1,69 млрд строк на графе из
   1037 вершин. Это включало JIT, который съедал 84 % времени запроса; лечили
   отключением JIT (ADR-010, `CB_DB_JIT=false`).
2. **Индексы.** Свойства лежат в одной колонке `agtype`. Индекс по `natural_key`
   подхватывается, только если выражение в запросе текстуально совпадает с
   `agtype_access_operator(...)`; `IN $keys` индекс не использует вовсе; GIN по
   всему `properties` читает общий для всех узлов posting list `namespace`
   (`GraphStore.ensure_label_index`).
3. **Конкурентная запись.** Конкурентный `MERGE` одной сущности падает с
   `Entity failed to be updated`, первая запись новой метки — с `DuplicateTable`
   или `UniqueViolation` на создании таблицы метки. Оба места закрыты
   advisory-локами.
4. **Перенос и бэкап.** `pg_dump` переносит в `ag_graph.graphid` и `ag_label.graph`
   OID старого кластера, и сервис падает с `graph with oid NNNNN does not exist`.
   При переезде стенда 2026-07-27 это чинили ручной правкой каталога AGE.
5. **Права.** Сервис на каждом подключении выполняет `LOAD 'age'`, а это разрешено
   только суперпользователю. В отдельном контейнере это незаметно, в общем кластере
   платформы — недопустимо: суперпользователь видит все базы.
6. **Сборка и версии.** Свой образ на базе `apache/age` с pgvector из исходников.
   Мажорную версию PostgreSQL определяет AGE, который отстаёт от релизов
   PostgreSQL.

### Что рассматривали 2026-10-02

Neo4j (как основное хранилище и как проекция для чтения), SurrealDB 3.3, готовые
системы памяти агентов (Graphiti, Cognee, Mem0, LightRAG, Hindsight, Neo4j Agent
Memory, SurrealDB Agent Memory). Готового движка, который закрывает видимость
факта по principal, журнал наблюдений с редакцией, сверку снимков без LLM и
воспроизводимый recall, нет; отдельная СУБД рвёт атомарность «наблюдение → факты →
индекс» и добавляет второй движок в поставку. Подробнее — раздел Alternatives.

## Decision

1. **Граф хранится в обычных таблицах базы памяти.** Имя графа (`CB_GRAPH_NAME`)
   становится схемой PostgreSQL, в ней две таблицы. Набросок:

   ```sql
   graph_nodes(
     id          bigint generated always as identity primary key,
     namespace   text not null,
     label       text not null,
     natural_key text not null,
     props       jsonb not null default '{}',
     ...,
     unique (namespace, label, natural_key)
   )
   graph_edges(
     id        bigint generated always as identity primary key,
     namespace text not null,
     type      text not null,
     src_id    bigint not null references graph_nodes on delete cascade,
     dst_id    bigint not null references graph_nodes on delete cascade,
     fact_id   text,
     props     jsonb not null default '{}',
     ...
   )
   -- рёбра фактов: unique (namespace, fact_id) where fact_id is not null
   -- структурные рёбра: unique (src_id, type, dst_id) where fact_id is null
   -- обход: (src_id, type), (dst_id, type); узлы: (namespace, natural_key)
   ```

   Свойства, по которым идут фильтры и соединения (`natural_key`, `namespace`,
   `fact_id`, `observation_id`, временны́е поля фактов), — колонки с типами;
   остальное — `jsonb`. Точный список колонок выводится из запросов `store.py` и
   `facts.py` при реализации. Метка — значение колонки, а не таблица: новая метка
   не требует DDL. `on delete cascade` даёт семантику `DETACH DELETE`.

2. **Upsert — `INSERT … ON CONFLICT`** по уникальным индексам п.1.
   Advisory-локи вокруг `MERGE` и создания меток удаляются.

3. **Обход** — как сейчас, итеративно по одному хопу: фронт передаётся массивом
   (`= ANY($ids)`) и идёт по индексам рёбер. Для запросов о пути разрешён
   рекурсивный CTE. Графовые алгоритмы остаются в networkx.

4. **Интерфейс не меняется.** Публичные методы `GraphStore` и `FactStore`,
   HTTP-контракт, Context API, доменные пакеты, видимость (ADR-019, ADR-021) и
   журнал наблюдений (ADR-016) остаются прежними. Cypher и `agtype` уходят из кода
   целиком. Когда в PostgreSQL появится SQL/PGQ (`GRAPH_TABLE`), его можно объявить
   поверх тех же таблиц без переноса данных.

5. **Перенос данных.** Одноразовая идемпотентная команда CLI читает таблицы меток
   AGE и пишет `graph_nodes`/`graph_edges` с сохранением `natural_key`,
   `namespace`, `fact_id` и свойств; в конце сверяет число узлов и рёбер по
   namespace. Выполняется, пока расширение AGE ещё установлено; данные AGE не
   трогаются. Удаление расширения и схемы графа AGE — отдельный шаг следующего
   релиза, после того как новая схема отработала на стенде. До этого шага откат —
   прежний образ сервиса.

6. **Приёмка по замеру.** Для таблиц реализуется протокол `GraphBenchOps`
   (`benchmarks/graph_ops.py`, ADR-016 §10) и прогоняется тот же `bench.py`, что и
   для AGE, на копии графа company-brain. Условие приёмки: ни одна операция
   (`entity_lookup`, `one_hop`, `two_hop`, `neighborhood`, `temporal_filter`) не
   медленнее AGE. Тот же прогон решает, нужен ли ещё `CB_DB_JIT=false`.

7. **Образ и права.** Образ базы памяти — PostgreSQL с pgvector, без AGE
   (официальный образ pgvector или общий образ кластера платформы). Сервис работает
   под обычной ролью — владельцем своей базы; расширения `vector` и `pg_trgm`
   создаёт шаг подготовки базы, а не сервис. `LOAD 'age'` и `search_path` с
   `ag_catalog` из подключения убираются.

## Реализация (TASK-001284)

Уточнения наброска п.1, принятые при реализации:

- **DDL** — `core/db.py` (`ensure_graph`): `CREATE SCHEMA/TABLE/INDEX IF NOT EXISTS` из
  кода, как у остальных таблиц сервиса; создаётся при первом обращении (дешёвая
  проверка каталога, создание — одной транзакцией под advisory-локом имени схемы,
  только на этом пути). `drop_graph` удаляет только `graph_nodes`/`graph_edges` и
  схему, если в ней больше ничего нет. Версия схемы и шаги догона — ниже, «Правки
  ревью TASK-001284».
- **Узлы:** колонки `namespace`, `label`, `natural_key`, `type`, `valid_from`,
  `valid_to` (`text COLLATE "C"` — моменты ISO-8601 UTC сравниваются побайтово, как
  раньше), `props jsonb` и вычисляемая `observation_id` = `props.props.observation_id`
  (redact и purge по наблюдению, ADR-001/002). В `props` — остальные свойства узла в
  прежнем виде (`title`, `source_path`, `origin`, …, свободные свойства — вложенной
  картой `props`), поэтому методы `GraphStore` отдают те же словари: колонки плюс
  `props`, пустые (NULL) поля не выдаются — как AGE, где `SET x = null` удалял свойство.
  Индексы: уникальный `(namespace, label, natural_key)`, `(namespace, natural_key)`,
  `(namespace, type)`, `(namespace, observation_id)`, GIN `props jsonb_path_ops`.
- **Рёбра:** `namespace` (у структурной связи — namespace её концов), `type`,
  `src_id`/`dst_id` с `on delete cascade`, `fact_id`, `observation_ids text[]`,
  `valid_from`/`valid_to`, `evidence_lost boolean`, `props jsonb`. Индексы:
  уникальные `(namespace, fact_id) where fact_id is not null` и `(src_id, type,
  dst_id) where fact_id is null`, обход `(src_id, type)`/`(dst_id, type)`,
  `(namespace, type)`, GIN по `observation_ids` и по `props`.
- **Конкурентная запись** без advisory-локов: upsert — `INSERT … ON CONFLICT`;
  чтение-слияние (scopes узла при записи через API, подтверждение факта новым
  наблюдением) — под построчной блокировкой (`FOR UPDATE`; для нового узла — сначала
  вставка строки своей метки, на ней ждёт параллельная запись того же ключа).
- **Метки:** `GraphStore.graph_labels()` перебирает различные `(namespace, label)` и
  `(namespace, type)` по индексам (рекурсивный skip scan), id метки — порядковый.
  Методы индексов меток AGE (`ensure_label_index` и кэш) удалены — метке DDL не нужен.
- **Соседство с AGE.** На установке с AGE схема `CB_GRAPH_NAME` уже есть и держит
  таблицы меток (`_ag_label_vertex`, `_ag_label_edge`, по таблице на вид и тип связи).
  Новые таблицы и индексы называются `graph_nodes*`/`graph_edges*`; если среди меток
  AGE окажется вид с таким именем, `ensure_graph` отказывает `GraphSchemaConflict`, а
  не пишет в чужую таблицу. Сервис данные AGE не читает и не трогает; читает их только
  команда переноса (п.5), и тоже без записи.
- **Предел ключа:** B-tree-индексы по `natural_key` ограничивают длину строки индекса
  (~2,7 КБ); в AGE ключ индексировался hash-индексом и длиной не ограничивался.
  Решение — ниже, «Правки ревью TASK-001284», п.2.

## Перенос данных (TASK-001285)

Команда `cb migrate-graph-from-age` (`graph/age_import.py`) выполняет п.5 на установке,
где граф ещё в AGE и расширение стоит.

- **Чтение без `cypher()` и каталога AGE.** Каждая метка AGE — таблица схемы графа,
  наследница `_ag_label_vertex` (`id graphid, properties agtype`) или `_ag_label_edge`
  (плюс `start_id`, `end_id`). Команда читает родительские таблицы, имя метки — имя
  таблицы строки (`tableoid`), значения — текстом (`::text`, функции вывода типов AGE;
  `LOAD 'age'` не нужен). Поэтому `ag_graph.graphid`/`ag_label.graph` со старого
  кластера после `pg_dump`/`pg_restore` переносу не мешают; битый каталог отмечается в
  отчёте с рецептом починки (для `cypher()`, если он ещё нужен). Обе таблицы читаются
  в одной транзакции `REPEATABLE READ`.
- **Сопоставление.** Текст `agtype` — JSON с аннотациями типа (`::numeric`, `::vertex`)
  вне строк; аннотации снимаются, `NaN`/`Infinity` (в jsonb не переносятся) — отказ
  разбора записи. Узел: метка — имя таблицы; `natural_key`, `namespace`, `type`,
  `valid_from`, `valid_to` — колонки, остальное — `props` в прежней раскладке. Узел без
  `namespace` получает namespace по умолчанию (`CB_DEFAULT_NAMESPACE`), как делал
  прежний `ensure_schema`. Ребро: тип — имя таблицы; у факта `fact_id`, `namespace`,
  `observation_ids`, `valid_from`, `valid_to`, `evidence_lost` — колонки; namespace
  структурной связи — namespace узла-источника. Значение не того типа колонкой не
  становится и остаётся в `props`.
- **id сохраняются.** Строка получает graphid своей вершины или ребра AGE
  (`OVERRIDING SYSTEM VALUE`); graphid меток не меньше 2^48 и с id генератора таблиц не
  пересекаются. После переноса генераторы продвигаются за перенесённые id. Без этого
  typed-контекст ссылался бы на структурные рёбра другими id (`edge:<id>` в
  `used.facts` — ядро хранит их как evidence), а порядок строк по id разошёлся бы с
  порядком AGE.
- **Факт на нескольких вершинах.** Прежний код искал концы факта по ключу без вида:
  у ключа с узлами нескольких видов один факт становился несколькими рёбрами с одним
  `fact_id`. В таблицах факт уникален в namespace (п.1) — переносится ребро между
  вершинами с наименьшими id (так выбирает концы `assert_fact` на таблицах), остальные —
  `duplicate_edge` в отчёте. Обход от узла другого вида того же ключа такой факт больше
  не находит — следствие уникальности факта, принятой в TASK-001284.
- **Идемпотентность.** `INSERT … ON CONFLICT DO NOTHING` пачками в отдельных
  транзакциях: повтор ничего не дублирует, доносит недостающее (в том числе после
  обрыва) и не перетирает строки, уже изменённые сервисом. Повтор допустим только
  при остановленном сервисе: после запуска сервис удаляет узлы (purge, prune), а AGE
  их хранит — повторный перенос вернул бы удалённое, включая вычищенные ПДн. После
  запуска сервиса — только `--dry-run`.
- **Сверка и отчёт.** По каждому namespace — узлы и рёбра в AGE, дубли (в таблицах —
  одна строка), пропущенные и в таблицах; ожидается «таблицы = AGE − дубли». Не
  переносится и попадает в отчёт: ключ длиннее предела (ниже, п.2) — без обрезки,
  запись без `natural_key`, неразбираемые свойства, ребро с пропущенным или
  отсутствующим концом. Расхождение или пропуск — код выхода 1; графа AGE нет,
  конфликт имён или ошибка БД — 2. `--dry-run` читает AGE и показывает сверку, ничего
  не создавая.
- **Удаление AGE** (следующий релиз) — не через `ag_catalog.drop_graph(…, true)`: он
  удаляет схему графа каскадом, то есть и `graph_nodes`/`graph_edges`. Удалять таблицы
  меток и строки каталога AGE по отдельности либо сначала перенести таблицы графа в
  другую схему.

Проверено интеграционными тестами (`tests/integration/test_age_import.py`): граф AGE с
несколькими namespace, видами, фактами с историей, структурными связями и временны́ми
полями переносится в те же узлы и рёбра, что пишет код на таблицах, и Context API
(`build_context`, typed-контекст) отвечает так же; повтор идемпотентен. Разово сверено
и с кодом до TASK-001284 (`a4dc7fe`) на AGE: typed-контекст после переноса совпал
полностью, включая `edge:<graphid>`; `build_context` — тот же состав разделов и
элементов, отличается только порядок внутри графового канала (прежний обход на AGE
отдавал соседей без порядка, на таблицах — по хопу и id) и зависящий от него
RRF-`score`.

## Правки ревью TASK-001284 (TASK-001285)

1. **`CREATE SCHEMA`** не выполняется, если схема уже есть (`to_regnamespace`): иначе
   роль-владелец готовой схемы без права CREATE на базу получала `InsufficientPrivilege`.
2. **Предел ключа — отказ, а не хэш.** Ключ узла длиннее 2048 байт UTF-8 и вид/тип связи
   длиннее 256 байт отвергаются до записи: `GraphKeyTooLong`, HTTP 400 с `detail`
   `natural_key_too_long: …` / `label_too_long: …` (а не 500 из
   `ProgramLimitExceeded`). С namespace до 200 символов строка индекса
   `(namespace, label, natural_key)` при этих пределах помещается в B-tree. Шагом схемы
   v2 добавлены `CHECK` (`NOT VALID` — существующие строки не перепроверяются) как
   страховка для записи в обход кода. Уникальность по хэшу ключа отклонена: она меняет
   все запросы по ключу (`= ANY`, `ON CONFLICT`) и индекс поиска по ключу, а ключи
   длиннее 2 КБ в памяти — ошибка потребителя (идентификаторы, пути, URL), а не данные,
   которые нужно хранить. Перенос (п.5) такие ключи не обрезает, а выносит в отчёт.
3. **`FactStore.facts(subject|obj)`** ищет конец в namespaces выборки
   (`a.namespace = ANY(…)`, `b.namespace = ANY(…)`) — по индексу
   `(namespace, natural_key)` и без концов из других баз.
4. **Защищённый `upsert_node`** держит `FOR NO KEY UPDATE`: ключ строки не меняется, и
   вставка ребра к узлу (проверка внешнего ключа берёт `FOR KEY SHARE`) не ждёт конца
   транзакции записи узла.
5. **Версия схемы.** Отметка — комментарий `platform-memory graph schema vN` на
   `graph_nodes`; быстрый путь `ensure_graph` — один запрос (отметка текущей версии и
   таблица рёбер на месте). Иначе под advisory-локом: проверка на чужие таблицы, шаги
   от сохранённой версии (`_STEPS`: 1 — таблицы TASK-001284, 2 — ограничения длины) и
   новая отметка. Таблицы без отметки — версия 1. Схема новее кода не трогается.
6. **Конфликт с метками AGE** проверяется до вывода «граф есть»: `graph_exists`
   признаёт таблицы своими по структуре (`natural_key`, `src_id`), таблица метки AGE
   отметки версии не имеет; `drop_graph` удаляет только свои таблицы.

## Замер (TASK-001286)

Отчёт — [`benchmarks/graph-engines.md`](../../benchmarks/graph-engines.md). Копии
company-brain у замера нет: граф сгенерирован в масштабе рабочей базы (27 365 узлов,
69 114 рёбер, хабы до 2 799 связей; `benchmarks/graph_gen.py`, детерминированно по seed),
записан в AGE раскладкой кода до TASK-001284 и перенесён `cb migrate-graph-from-age`; обе
стороны — в одной базе. `GraphBenchOps` реализован для обоих движков
(`benchmarks/graph_ops.py`), гибридный запрос — `build_context` с графом компилятора на
каждом движке; прогон — `bench.py engines`.

- **Приёмка п.6 — условная, на синтетическом графе.** Это отклонение от текста п.6
  (прогон на копии company-brain): копия рабочей базы к замеру не выдана. На синтетике
  ни одна операция на таблицах не медленнее AGE ни по p50, ни по p95: `entity_lookup` и `temporal_filter` — в 4 раза быстрее, `one_hop` — в 185,
  `neighborhood` — в 440, `two_hop` — в 5 000 (у AGE `[*1..2]` от хаба — 35–70 с),
  гибридный запрос — 0,5 с против 111 с. Ответы движков на выборке совпадают.
- **`CB_DB_JIT=false` для графа не нужен.** Самая дорогая оценка плана на таблицах —
  8 291 при `jit_above_cost` 100 000, JIT не включается ни в одном запросе, разница
  `jit=on`/`off` — в пределах шума. Снятие обхода из `core/db.py` (`session_options`) —
  отдельное изменение после удаления AGE: на общем кластере JIT регулирует его настройка,
  а не сессия сервиса.
- **Контрольный прогон на копии company-brain обязателен перед выкаткой** (TASK-001293):
  на восстановленном дампе рабочей базы, после переноса `cb migrate-graph-from-age` и до
  переключения образа сервиса, той же командой (`bench.py engines --dsn`, раздел
  «Повторить» отчёта). Если хоть одна операция на таблицах медленнее AGE по p50 или p95,
  выкатка останавливается, а задача возвращается владельцу с планами
  `EXPLAIN (ANALYZE, BUFFERS)` и предложением индексов. Цифры прогона дописываются сюда
  и в отчёт.

### Контрольный прогон на копии staging, 2026-10-03

Прогон перед выкаткой на staging (TASK-001293), цифры записаны TASK-001370; подробно —
одноимённый раздел [отчёта](../../benchmarks/graph-engines.md). Копия базы памяти staging:
1 619 узлов, 2 552 рёбер (из них 2 549 фактов), 5 namespace. Перенос
`cb migrate-graph-from-age` — сверка сошлась, расхождений 0. Железо — ноутбук (Apple M4,
фоновая нагрузка ~8).

- Namespace графа `…:ws:4a46…`: все операции на таблицах (`jit=off`, дефолт) быстрее AGE
  (`jit=off`, как работал сервис) и по p50, и по p95 — от 2,5 раза (`entity_lookup` по
  p50: 0,55 против 1,39 мс) до 21 раза (`temporal_filter` по p95).
- **Гибридный запрос в `tenant:4796…`** (19 697 наблюдений, без чанков) — единственное
  место, где таблицы хуже AGE: в первом прогоне p95 130,9 против 113,5 мс (p50 — 65,7
  против 83,8). Повтор в обратном порядке конфигураций — таблицы 48,1 / 90,7, AGE
  87,3 / 201,5. По `EXPLAIN (ANALYZE, BUFFERS)` графовая часть на таблицах занимает
  < 0,5 мс против ~40 мс у AGE; время — в канале наблюдений, SQL которого у движков
  одинаковый. Формально это срабатывание стоп-условия выше (p95 таблиц хуже AGE).
- **Решение владельца 2026-10-03:** разница p95 в `tenant:4796…` — шум машины, а не
  движка (знак меняется на повторе, графовая часть на таблицах в 80 раз дешевле);
  выкатка на staging одобрена.
- Попутно найдено и исправлено в TASK-001370: канал recent наблюдений (Context
  Compiler) сортировал по текстовому алиасу `ingested_at::text` и читал таблицу
  наблюдений целиком (`Seq Scan`, 16,6 мс на 19,7 тыс. строк). Теперь порядок — по
  колонке `ingested_at`, а top-N каждого namespace читается индексом
  `<observations>_ns_recent (namespace, (occurred_at = ''), occurred_at DESC,
  ingested_at DESC)`. Бенчмарк (`benchmarks/engines.py`) берёт тексты гибридного
  запроса из наблюдений, а без них — из `natural_key` узлов, если в namespace нет чанков
  (на копии staging крупнейший namespace без чанков давал `ZeroDivisionError`).

## Consequences

Плюсы:

- нормальная статистика и планы, индексы по типизированным колонкам;
- честный upsert без гонок и без локов-обходов;
- `pg_dump`/`pg_restore` работают без ручной правки каталога;
- сервис не требует суперпользователя и встаёт в общий кластер платформы;
- версия PostgreSQL больше не привязана к AGE, свой образ с AGE не нужен;
- вектор, полнотекст, граф и видимость можно собирать одним SQL-запросом.

Минусы и цена:

- переписать слой графа (около 2800 строк) и его тесты;
- Cypher уходит: произвольные графовые запросы вручную пишутся на SQL до появления
  SQL/PGQ в PostgreSQL;
- шаг переноса данных на каждой установке с графом AGE: staging, шаблон тестовой
  графовой базы узла fleet, витрины memory-demo и company-brain;
- обход переменной длины без кода AGE на C. Сейчас не используется (п.3), но при
  появлении глубоких обходов их стоимость нужно мерить отдельно.

## Alternatives

- **Оставить AGE.** Проблемы из Context никуда не уходят, а п.5 (суперпользователь)
  не даёт объединить базы платформы.
- **Neo4j основным хранилищем.** Отдельная СУБД рвёт атомарность «наблюдение →
  факты → индекс» и требует двойной записи между хранилищами — от постоянного
  dual-write суперпроект отказался по тем же причинам (TAI-ADR-0002, TAI-ADR-0017); онлайн-бэкап,
  кластер и RBAC — только в Enterprise; переписать пришлось бы весь слой хранения
  (около 6000 строк с журналом, индексом и снимками), а не только граф.
- **Neo4j как пересобираемая проекция для чтения.** Не отвергнуто, а отложено:
  понадобится, если продукт потребует глубоких обходов и алгоритмов в базе на
  больших графах. Таблицы п.1 остаются источником истины.
- **SurrealDB 3.3.** По функциям близко (граф, векторы, BM25 с русским
  стеммером, RRF, права на записи, события в транзакции), но 3.x вышла в феврале
  2026, в бесплатной версии нет отказоустойчивости и восстановления на момент
  времени, Python SDK под 3.x в бете, у вендора закрытый конкурирующий продукт
  памяти. И это второй движок в поставке рядом с PostgreSQL остальных сервисов.
- **Готовая система памяти вместо своего сервиса** (Graphiti, Cognee, Mem0 и др.).
  Ни одна не даёт видимость отдельного факта по principal, детерминированную
  сверку снимков внешних систем и воспроизводимый recall. Ближе всех Graphiti, но
  он требует Neo4j или FalkorDB. Из них заимствуем приёмы (инвалидация фактов по
  времени, сигналы ранжирования), а не движок.
- **LadybugDB (встраиваемый).** Отклонён спайком [ADR-015](ADR-015-ladybugdb-spike-rejected.md).

## Открытые вопросы

- **Запросы агентов на Cypher поверх таблиц** (предложение владельца
  2026-10-03). **Решено:** TAI-ADR-0069 суперпроекта (принято владельцем
  2026-10-03) — `cypher-read/1` через ядро; детали движка — отдельный MEM-ADR. С уходом AGE теряется встроенный Cypher, а модели пишут его
  хорошо: шаблон `MATCH (a:Company)-[:SUPPLIES]->(b) WHERE … RETURN …` агенту
  понятнее собственного языка запросов. Вариант — транслятор подмножества
  openCypher **только на чтение** (`MATCH`, `WHERE`, `RETURN`, `ORDER BY`,
  `LIMIT`, пути с верхней границей `*1..N`; запись — по-прежнему только через
  ingest с происхождением) в параметризованный SQL по `graph_nodes`/`graph_edges`.
  Разбор — по готовой грамматике openCypher, без своего парсера. Обязательные
  условия:
  - фильтры namespace и видимости ([ADR-019](ADR-019-principal-visibility-via-policy-service.md),
    [ADR-021](ADR-021-client-visibility-narrowing.md)) подставляет транслятор, агент
    их не обходит;
  - пределы глубины, числа строк и `statement_timeout` с внятным отказом;
  - доступ — маршрутом memory-service через ядро (как recall) и инструментом
    MCP для агентов.

  Решать отдельным ADR после выкатки таблиц на staging и замера п.6: схема к
  этому моменту окончательная, бенчмарк покажет, какие обходы дешёвые.
