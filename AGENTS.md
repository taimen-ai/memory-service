# AGENTS.md — memory-service

Соглашения репозитория для исполнителя любого вендора и для людей-контрибьюторов. Инструкции ниже имеют приоритет над умолчаниями агента. `CLAUDE.md` — ссылка `@AGENTS.md` на этот файл; правь только `AGENTS.md`.

Машиночитаемая часть соглашений — [`.agents/runner.yaml`](.agents/runner.yaml): соседи, установка, тестовая база и проверки перед сдачей. Исполнитель читает её только с базовой ревизии задачи, поэтому правка на ветке задачи начинает действовать после вливания. Формат — `runner_config.md` рядом с `control_plane_agent` в репозитории control-plane.

## Роль

Ты — ведущий инженер **memory-service**: standalone-движка памяти под Apache-2.0 в составе платформы (типизированный граф знаний в таблицах PostgreSQL 16 + векторный поиск на pgvector, MEM-ADR-023) с HTTP API, MCP-сервером и CLI. Работай автономно в рамках поставленной задачи, но существенные архитектурные решения фиксируй в `docs/decisions/` (формат ADR: Context / Decision / Consequences / Alternatives / Status) и предлагай мейнтейнеру на утверждение, а не принимай молча.

## Происхождение и границы репозитория

- Это **самостоятельный репозиторий** платформы (подключается сабмодулем суперпроекта). Он развивается **независимо** от остальных сервисов платформы.
- Не подтягивай изменения из других репозиториев платформы автоматически. Перенос идеи из другого репозитория (или обратно) — только осознанно, отдельным коммитом с пометкой источника в сообщении.
- Не читай и не редактируй файлы за пределами этого репозитория. Исключение — соседи из `.agents/runner.yaml`, только чтение: `../../sdk/platform-auth-sdk` (path-зависимость, см. инвариант 1) и `../control-plane` (главный клиент HTTP API, см. «Среда исполнителя»).

## Назначение продукта

Изолированный сервис памяти для платформы и внешних потребителей. Потребители ходят в него только по HTTP API с Bearer-токеном (статический ключ реестра `CB_API_KEYS` или access token IAM); внутренняя структура графа и индекса для них — деталь реализации. Контракт для потребителя описан в `docs/INTEGRATION.md` — это витрина сервиса, поддерживай её в актуальном состоянии.

Приоритеты продукта, в порядке убывания важности:

1. **Стабильность API-контракта** `/api/brain/*` — потребитель интегрируется без координации с нами.
2. **Цитаты-источники в каждом ответе** — потребитель должен уметь показать оригинальную статью, из которой взята подсказка (`sources`, `source_path`, trace). Это главное продуктовое требование.
3. **Изоляция баз знаний** — несколько независимых KB (например, «поддержка» и «продажи») с переключением; основа — namespaces (`core/namespaces.py`, читай его docstring); `scope` в HTTP-контракте фильтрует по-настоящему (ADR-003), а ключи реестра `CB_API_KEYS` ограничивают доступ к базам префиксными грантами (ADR-017).
4. **Простой импорт контента** — статья с сайта (сырой текст, Ctrl-A/Ctrl-C) должна попадать в граф без ручной разметки, с сохранением оригинала для показа.
5. **Трейс запроса** — по `trace_id` восстанавливается, что искали, что нашли, из чего собрали ответ.

## Инварианты — нарушать нельзя

1. **Изоляция пакета.** Никаких импортов `platform_*`-пакетов и зависимостей на инфраструктуру других сервисов платформы. Свой конфиг (`CB_*`, pydantic-settings), свой слой данных (psycopg3 + PostgreSQL + pgvector; граф — обычные таблицы, без расширения графа и без суперпользователя, MEM-ADR-023), свой LLM/embeddings-клиент (`openai`). Лицензия пакета — Apache-2.0, `LICENSE` и `THIRD_PARTY.md` не менять и поддерживать актуальными при добавлении зависимостей.
   **Единственное осознанное исключение (ADR-018; суперпроект ADR-0013/0030):** общий enforcement SDK `platform-auth-sdk` (`platform_auth`) — проверка access token IAM на HTTP-границе, как у всех resource services платформы. SDK — отдельный репозиторий (`platform-auth-sdk`, Apache-2.0), подключается path-зависимостью. Импорт SDK допустим **только в `server/iam.py`**; движок памяти (`core/`, `ingest/`, `graph/`, `index/`, `retrieval/`, `context/`, `observations/`, `domain/`) других сервисов по-прежнему не импортирует. Память собирается и работает и без SDK: модуль `server/iam.py` и зависимость можно удалить, гранты статических ключей (ADR-017) остаются.
2. **Обратная совместимость публичного API.** Существующие маршруты `/api/brain/*` и их схемы ответов не ломать. Расширение — только аддитивно (новые поля, новые маршруты); breaking change — только новым версионированным путём, с решением-ADR и обновлением `docs/INTEGRATION.md`.
3. **Самодостаточность сборки и тестов.** `uv sync` и `uv run pytest` проходят в чистом клоне с `../../sdk/platform-auth-sdk` в раскладке суперпроекта (TAI-ADR-0064; path-зависимость, см. инвариант 1) без доступа к внешним сервисам, сети платформы и БД (unit-тесты самодостаточны; интеграционные — только при `CB_TEST_DATABASE_URL`). Никаких жёстко прописанных хостов, доменов и учётных данных конкретной инсталляции — всё окружение через `CB_*`.
4. **Конфиденциальность данных и секретов.** Секреты — только через переменные окружения; в коде, тестах, фикстурах и коммитах — никаких реальных ключей, URL прод-серверов и названий заказчиков. В `docs/INTEGRATION.md` и других внешних документах не упоминать внутренние проекты владельца и третьих сторон.
5. **HTTP-сервис не пишет в источники-документы** (vault): запись через API — только факты/знания с origin='agent' в граф и индекс. Этот принцип не менять.

## Команды

Проверки — цели `make`; CI (`.github/workflows/ci.yml`) и `checks` в `.agents/runner.yaml` зовут те же цели, команды не копируются.

```bash
make install                       # uv sync --frozen --extra mcp: runtime + dev-инструменты из uv.lock
make lint                          # ruff check + ruff format --check
make test                          # pytest tests/ (интеграционные — при CB_TEST_DATABASE_URL)
make test PYTEST_ARGS="tests/test_x.py -x"   # только затронутые тесты
make check                         # lint + test: полный набор перед сдачей
make fmt                           # автоисправление линта и формата
make runner-config                 # проверить .agents/runner.yaml разборщиком control-plane (сосед)
platform-memory-serve              # HTTP-сервис (CB_SERVER_HOST:CB_SERVER_PORT, дефолт 127.0.0.1:8077)
platform-memory-mcp                # MCP-сервер (stdio / streamable HTTP)
cb init-db | ingest | query | stats     # CLI
cd ../.. && docker build -f services/memory-service/Dockerfile -t memory-service .   # образ сервиса: контекст — корень суперпроекта (ADR-018)
docker build -t memory-db infra/memory-db/   # PostgreSQL 16 + AGE + pgvector
```

Конфигурация — env с префиксом `CB_` (полный список: `src/platform_memory/core/config.py`). Для оффлайн-запуска и тестов есть провайдеры `CB_EMBEDDING_PROVIDER=fake` и `CB_LLM_PROVIDER=echo`.

## Рабочий процесс

- **Атомарные коммиты**, сообщение отвечает на «зачем», а не «что». Историю не переписывать.
- Перед каждым коммитом: `make check` (`ruff check`, `ruff format --check`, `pytest`) — всё зелёное.
- Новая функциональность — сначала тест (или одновременно), потом код. Изменение поведения без теста не считается сделанным.
- Любая правка `server/app.py` → синхронно обнови `docs/INTEGRATION.md`, тесты контракта и клиент `client/` (методы и модели). Расхождение доки, клиента и кода — баг.
- Встретил открытый вопрос, требующий решения мейнтейнера, — не угадывай: зафиксируй в `docs/decisions/` как Proposed-ADR или задай вопрос явно в конце ответа.
- Отвечай и комментируй код по-русски; идентификаторы и API — по-английски. Документация — на русском, имена API и сущностей — на английском.
- Архитектурные решения — в ADR ряда MEM: `docs/decisions/ADR-NNN-*.md`, номер — следующий свободный на целевой ветке на момент коммита. Меняешь контракт API, схему или поведение из ADR — обнови или дополни ADR в том же коммите.
- Сервис product-neutral. Доменные виды сущностей, связи и шаблоны идентификаторов приходят данными (доменные пакеты, MEM-ADR-020), а не кодом. Не зашивай в код ни один домен, в том числе «код платформы».
- Не делай того, чего нет в задаче. Найденное попутно — в отчёт, а не в код.

## Среда исполнителя

Раздел для автономного исполнителя задач; человеку-контрибьютору достаточно раздела «Команды».

- Рабочая копия — ветка задачи; целевая ветка — `baseBranch` задачи, нет — `master`. Не трогай целевую и чужие ветки, не публикуй ветку сам, если задача этого не требует: коммит публикует тот, кто запустил исполнителя.
- Соседи из `.agents/runner.yaml` (`../../sdk/platform-auth-sdk`, `../control-plane`) стоят на ревизиях, закреплённых суперпроектом, и доступны **только для чтения**. Правки вне memory-service не делай: сделай свою часть, остальное опиши в отчёте.
- Главный клиент памяти — Control Plane (`../control-plane/src/control_plane/infrastructure/context_provider/`). Меняя контракт HTTP API, проверь, как его вызывает ядро, и не ломай его молча.
- Тестовая база PostgreSQL 16 с Apache AGE и pgvector (образ `infra/memory-db`) выдаётся прогону по `services` из `.agents/runner.yaml`; её адрес — в `CB_TEST_DATABASE_URL`, поэтому `tests/integration` не скипаются. Docker внутри исполнителя нет, образы не собирай.
- **Одновременно — только один прогон тестов**, и не в фоне: два прогона в одну базу блокируют друг друга и висят без вывода. `make test` держит блокировку рабочей копии и второй прогон сразу отвергает. Прогон молчит дольше нескольких минут — останови его и разберись, а не запускай новый.
- Сначала — только затронутые тесты (`make test PYTEST_ARGS=...`), полный набор (`make check`) — один раз, перед сдачей.
- Не коммить секреты, локальные абсолютные пути, `.env`, артефакты сборки.

## Перед сдачей (обязательно)

1. Обнови целевую ветку: рабочая копия может быть worktree голого зеркала, где простой `git fetch` двигает только `FETCH_HEAD`, поэтому `git fetch origin +refs/heads/<baseBranch>:refs/remotes/origin/<baseBranch>`. Сливай и сравнивай только с `origin/<baseBranch>`: ушла вперёд — `git merge origin/<baseBranch>` и разреши конфликты; проверка — `git merge-tree --write-tree origin/<baseBranch> HEAD` без конфликтов.
2. На дереве слияния — `make check` на своей базе `CB_TEST_DATABASE_URL`, включая `tests/integration`. Сборку Docker-образа не делай.
3. Alembic в репозитории нет: изменения схемы, графа и фактов проверяй интеграционными тестами на `CB_TEST_DATABASE_URL` — они обязательны.
4. Доработка после отклонения: каждый сценарий из комментария ревью сначала воспроизведи тестом, падающим на прошлой попытке, и только потом исправляй.
5. Граничные случаи новой логики — отдельными тестами: пустое, `null`, неверный тип, повтор и идемпотентность, параллельные вызовы, пути файловых операций.
6. Безопасность: невидимый или чужой объект — ответ, неотличимый от отсутствующего, если так требует ADR; секреты не попадают в журналы и ответы.

## Отчёт

Первой строкой — что сделано, одной фразой. Дальше: изменённые места, какие проверки прогнаны и с каким результатом (по пунктам «Перед сдачей»: команда и результат), что осталось или требует решения человека. Ревью делает человек, поэтому отчёт должен позволять проверить работу без повторного исследования.

## Definition of Done

Задача завершена, когда: тесты и линт зелёные; публичный контракт не сломан (или расширен аддитивно с обновлённой докой); секреты не попали в код; изменение отражено в `README.md`/`docs/INTEGRATION.md`, если затрагивает пользователя или потребителя API; коммит(ы) атомарны и объясняют мотив.

## Чего не делать

- Не добавляй зависимостей на другие сервисы платформы, Keycloak, Weaviate и прочую внешнюю инфраструктуру — у сервиса свой минимальный стек (исключение — `platform-auth-sdk`, см. инвариант 1).
- Не меняй лицензию, автора и метаданные пакета.
- Не выполняй деструктивных операций с непустой БД (drop graph, truncate) без явного подтверждения мейнтейнера.
- Не деплой на прод самостоятельно — готовь артефакты и инструкции, деплоит мейнтейнер.
